# Privacy request and review recovery

Authenticator setup: when a successful inventory read has no factors, Profile and inline Privacy show a prominent **Set up authenticator** button with three setup steps, instead of an empty selector and disabled verification form. Start setup, scan the displayed QR code in an authenticator app, then enter its six-digit code and choose **Finish setup**. Existing factors use the selector/code form; unfinished factors explain how to verify or clear and restart. Loading and unavailable reads are distinct from an empty inventory. Uncertain enrollment still requires reconciliation before another setup. This presentation change needs no migration; hosted enrollment and browser acceptance remain pending.

Settings Privacy now keeps request/review input through temporary failures. If a write response is lost or invalid, **Recover original save** repeats the same parsed payload and request key. Other save/search/case-switch controls stay disabled until that original operation is resolved. If a verified write succeeds but the case list refresh fails, **Load saved records** retries reads only. Success feedback, clearing the submitted form and closing the review happen after the fresh list loads. Request saves preserve separate review input; review saves preserve separate request input.

A definitive validation/version conflict releases recovery so the user can correct fields or refresh records and reselect the current case version. A recent-authenticator requirement retains the original privacy payload and request key. Use **Verify authenticator here** in Privacy, then explicitly recover the original save. Setup/verification stays outside the disabled request/review fieldset, so retained forms remain mounted. Verification never automatically submits a privacy change. Profile account security remains available. Mounted recovery is in memory: leaving Privacy, switching agency/role or reloading the page discards it. Database scope/replay/versions and recent MFA still authorize every mutation; this change adds no deletion or agency-closure operation.

Case lists, review history and lead choices validate response shape before publication. Case lists bind tenant, case state, versions and timestamps and reject execution-enabled responses. Review history is bound to the selected case request and current request generation. Lead choices bind tenant and active/archived search mode; changing search text or archive mode clears choices and selected lead. Malformed or failed reads are shown as unavailable rather than a successful empty result. Temporary errors may retain a previously verified list with the error visible.

Separate current-request controllers cover the parent workflow and selected-case history. A synchronous action gate blocks duplicate submissions before React renders a busy state. Abort/generation checks prevent ignored-abort responses from effect replay, unmount, scope replacement or a former case/query from publishing. Same-case refresh preserves review input; selecting a different case clears that case's review inputs. Current authentication/role denial clears protected lists, choices, review inputs, pending recovery and impact preview and fences concurrent old responses. Explicit access reload can resume only after a new successful case read. Recent-MFA errors are distinguished from access revocation.

Thirteen checks execute actual client helpers with injected/deferred transport, including immutable original replay, read-only post-save recovery, invalid receipt binding, duplicate-action prevention and stale responses. An actual local SQL fixture passes request, review, hold, release and withdrawal receipts through the client validators. Types and production build verify component integration; these tests do not mount React, validate keyboard/focus/DOM behavior or prove hosted Auth/browser/multi-agency acceptance. LOCAL_CHECKS.json records the final full verification result. Schema remains 001–023; no new migration or private environment change is required.

Inline authenticator verification (P8 nineteenth slice): Privacy offers an expandable setup/verification panel using the shared account-security component. The exact 403 RECENT_MFA_REQUIRED write response preserves the original save key/payload, opens inline verification and keeps submitted inputs disabled until explicit recovery. Other authorization denials still clear protected scope. Parent and authenticator synchronous guards prevent overlapping saves/verification before busy UI renders. Selected-factor preflight, explicit verification POST and fresh recent/verified inventory are all required before success. Failed verification retains the code; successful verification clears it. Explicit factor refresh can reconcile a lost verification acknowledgement with reads only. Callback tickets fence unmount/scope changes; private setup/code/factors stay in mounted memory. Verification success preserves request/review inputs and requires an explicit save/recovery click. No new SQL or environment change is required. Eight new helper/replay/deferred checks pass alongside existing recovery checks; types/build establish integration, not mounted DOM/hosted Auth/browser acceptance.
