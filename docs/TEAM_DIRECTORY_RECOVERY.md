# Settings team directory recovery

The supplied Settings Privacy screenshot showed a database error above the Privacy panel while its case list had loaded. Existing development server output records `GET /api/v1/team` as 200, `/api/v1/team/members?limit=25` as 503 and `/api/v1/privacy` as 200. The error therefore comes from the parent Settings team load rather than proving that migration 022 failed. No new browser or hosted API request was made to collect this observation.

The pre-023 team directory selects `auth.users.email` directly into a declared `email text` return column. Supabase's [Auth schema](https://github.com/supabase/auth/blob/master/migrations/00_init_auth_schema.up.sql) defines email as `varchar(255)`. A local database with that column type reproduces SQLSTATE 42804 in `RETURN QUERY`; the earlier synthetic `text` fixture hid the mismatch. The hosted SQLSTATE has not been independently captured, so this is a reproduced compatibility defect consistent with the observed failing endpoint.

Migration `backend/supabase/migrations/202610100023_team_email_type.sql` explicitly returns `u.email::text`. It preserves the function signature, grants, verified lock-free membership check, manager/agent scope, sorting, pagination and workload counts. It changes no customer records or Auth columns. The shared current-schema local fixture and fresh-bundle fixture now use `varchar(255)`; the historical migration 021 test explicitly retains its old text fixture to isolate its earlier locking defect.

For an initialized development project already through 022, apply only migration 023 once in Supabase SQL Editor. Then use the top Settings **Refresh** button to retry the parent team load.
