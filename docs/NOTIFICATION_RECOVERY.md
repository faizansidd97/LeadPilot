This improves Notifications inbox and its workspace badge; it does not trigger jobs, send messages, change recipient permissions or require a new key/migration. ## Snapshot, paging and visibility

The mounted inbox owns one agency request controller and a synchronous read/action gate. List and unread summary reads both succeed and validate before rows/cursor/count publish. Failure is unavailable history, with an unknown badge, rather than a confirmed empty or caught-up inbox. Previously loaded rows remain in memory during a recoverable failure, but sensitive resource labels/due previews are hidden and row actions disabled until refresh/recovery. Definitive 401/403/404 recipient denial clears rows, cursor and pending save. Agency changes/unmount and effect replay fence ignored-abort completions.

Rows project only display fields, with bounded IDs/types/timestamps/versions, filter membership, current/access preview consistency and duplicate checks. Pages contain at most 25 rows, ordered by exact PostgreSQL timestamp precision and UUID; the cursor binds the full last timestamp/ID. Paging uses the same gate as refresh/filter/actions and cannot append overlap or forward rows. SQL rechecks recipient membership/RLS; list and update projections do not include tenant/recipient IDs and do not constitute independent client proof of those permissions. List and summary are separate statement snapshots, not an atomic database-wide view.

The inbox polls every 45 seconds only while visible, ready, idle and without pending recovery. An unavailable read stops automatic polling until explicit refresh. Outside Notifications, the workspace badge polls a validated summary every visible minute with its own current-request/action ticket. Entering Notifications closes that background reader; its late response cannot overwrite the inbox's count. Unknown counts are hidden and labelled unavailable for assistive navigation rather than represented as zero. No notification failure blocks manual CRM in other sections.

## Read, dismiss and opening

Read/dismiss keeps the original serialized body, notification version, endpoint and request key after uncertainty. Same-frame duplicate actions, filter changes and alternate operations cannot replace it. Only Recover can repeat an uncertain PATCH. A verified acknowledgement followed by failed list/summary refresh retains a read-only recovery. Success notice waits for refreshed validated state; stale visible rows cannot acknowledge the receipt. Definitive validation/version denial releases the operation and requires explicit refresh before a new attempt. Existing read/dismiss markers are compared at full timestamp precision.

Open latest first reauthorizes the recipient notice and loads the authorized lead, projecting only workspace fields. An unread notice then uses the same read-save recovery, refreshes the inbox/count and reauthorizes/reloads the destination again before navigation. A lost acknowledgement or subsequent read failure never opens cached preflight data. Recovery repeats only the original uncertain read-save or, after acknowledgement, reads. If resource access disappears, refreshed redacted notices and an unavailable message replace navigation. Already-read notices open through current read-only checks. Team targets require the server's current authorized team result. Workspace callbacks receive the verified row synchronously, with no separate late lead request.

Leaving the inbox or changing agency discards in-memory recovery. Aborting cannot cancel an already committed SQL PATCH. Replay still rechecks current server recipient identity, membership, version/hash and operation; there is no durable browser retry queue or cross-tab cookie lock. No token/customer payload is stored in browser storage.
