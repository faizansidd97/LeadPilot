## Read and save behavior

The workspace's verified actor/agency/role mounting and Capture's agency/role/mode mounting isolate state. Cancellable current tickets and a synchronous action gate fence read/save/recovery completions. Metadata and assignment choices publish together only after both validate. Metadata is projected to public fields, bounded to the existing twenty-integration policy, unique and ordered by full-precision creation time descending then UUID ascending. The projected active-member directory has unique IDs, supported roles and bounded labels; a defensive 10,000-row client limit fails closed. It does not independently prove email verification or tenant identity. The actual SQL rechecks verified manager authority, active verified assignee eligibility and tenant scope.

Confirmed empty differs from unavailable. Failed reads hide unverified integration identities, versions and signing material and disable forms. Existing create/name/assignment and per-integration reason/action forms remain mounted through temporary failures. Only complete current workflows reset their original form. Capture tabs and Settings tabs/refresh are synchronously locked while website work or pending recovery exists. Closing or root navigation still discards mounted attempts and cannot undo a committed transaction.

Create/rotate/revoke capture parsed immutable input, original selected version and a random request key before awaiting. A lost or malformed acknowledgement retains that original operation. Explicit recovery repeats only its original request, rather than capturing changed form data or minting another key. The server's actor/tenant/operation/payload/issuance replay checks govern whether replay remains valid. Superseded signing credentials, access changes and stale versions can produce definitive rejection; refresh saved state before further changes.

A valid acknowledgement binds create name/assignment and initial versions, or change identity/name/assignment/creation time and exact next versions/active state. Create/rotate require a bounded lowercase 64-character signing secret; revoke must not contain one. Unexpected response properties are discarded. An acknowledged save moves to read recovery: failed metadata/directory reads never repeat create, rotate or revoke. A snapshot behind acknowledged versions cannot complete recovery. A newer, revoked or missing integration hides/discards the earlier secret and explicitly reports that the acknowledged operation is no longer the current state.

## Private signing receipts

Signing material is held only in mounted memory. It is hidden while reading, during errors and until the current paired snapshot matches the receipt's integration ID, name, assignment, creation time, active state, version and key version. Matching metadata is a client consistency check, not cryptographic proof of the secret or an atomic cross-tab authorization lock; SQL issuance/current-secret checks remain authoritative. Another manager can change the integration after the read. Refresh before further work.

Hide secret clears its mounted private holder permanently; later list refresh does not reconstruct it. A fresh separately requested rotation can issue a replacement under server policy. Current 401/403/404 clears metadata, assignment choices, private signing material, original recovery and completion callbacks. Scope changes/unmount fence ignored-abort late responses and cannot redisplay a secret or reset a form in the new scope. No secret, request key or form data is written to browser storage. Existing endpoint/manual selection instructions remain; this slice adds no automatic clipboard or website connection.
