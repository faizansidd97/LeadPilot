# Client workflow recovery

P8 hardens local request recovery in Capture, Settings, the authenticated workspace and lead detail. Existing cookie identity, current tenant/role checks, SQL replay scope and audit remain the server authority. The client helpers do not grant access or replace database permissions. Client recovery changes no schema; the current fresh setup includes 001–021. Historical slice notes below retain their original migration boundaries.

## Recovering a save

Previously both panels forgot a mutation key immediately after the save response. If the following detail/list refresh failed, repeating the same action could create a fresh import/integration or issue another invitation change. The shared MutationRetry helper now retains the exact tenant/path/method/payload identity through both the write and required follow-up reads. A lost acknowledgement or post-save read failure reuses that key when the user retries the same inputs. Only a completed current-scope workflow acknowledges and clears the attempt. An unrelated successful read does not discard it; changed tenant/path/method/payload starts a different operation.

Capture binds import preview/process/resume/retry and website create/rotate/revoke to this workflow. CSV mapping/input is cleared only after the saved preview and lists load successfully; selecting a new file immediately clears the old mapping and preview before asynchronous parsing. Settings retains mutation identity through team/list refreshes and only shows the completed save notice/ends editing after those reads succeed. Authoritative saved rows may already have changed when an error is shown; exact retries and saved operation history are the recovery paths.

Retries are held only in the mounted panel's memory. No payload, CSV, bearer link, signing secret or retry identity is persisted in browser storage. Navigation/unmount/authorization reset can discard the attempt; after returning, inspect saved operations/current records before repeating uncertain work. This is not an automatic retry scheduler or an exactly-once guarantee across sessions. SQL current-authority checks still apply to every receipt replay.

## Delayed responses and access changes

The ClientRequests helper issues abortable generation tickets. Cleanup aborts and invalidates the old generation; a subsequent effect cannot reactivate its old responses even if the transport ignores cancellation. Guards run after reads/writes before setting state or continuing follow-up work. Capture mounts a fresh internal scope for tenant/role/mode changes; Settings mounts a fresh tenant scope. Role changes in the authoritative Settings snapshot clear team/invite/link/edit caches and move unavailable tabs to Profile. HTTP 401/403 clears protected cached data and secret/link receipts. Capture also clears CSV/mapping/preview and invalidates pending file parses on denied access.

A synchronous action gate prevents a second save/resume/paging/refresh from entering before React renders its busy state. Stale cleanup cannot unlock a newer action. Closing a scope prevents late queued actions from reopening it; only a new effect scope can resume. Tabs are disabled during active workflows so a delayed secret/link receipt is not applied to another active tab. These client controls do not recall a server mutation already committed before abort, undo a saved operation or revoke copies already taken.

## Transport errors

requestApi merges Headers objects correctly while enforcing the explicit tenant and idempotency parameters, and retains no-store fetching. Network loss becomes a safe connection-interrupted retry message. HTML or malformed proxy responses become safe errors rather than raw JSON parser/proxy content; HTTP 401/403 is preserved for cache invalidation. Successful responses require a data envelope without an error field. Authorized backend field/conflict/rate messages remain available, including Retry-After metadata. Explicit aborts remain aborts and stale panel generations suppress their UI effects.

## Authenticated workspace recovery

The tenth P8 slice extends the shared abort/action tickets to ConnectedWorkspace. Bootstrap, agency switching, context refresh, account actions and sign-out check their generation after every asynchronous boundary. Transitions hide the mounted private workspace before loading another scope. A synchronous action gate rejects same-frame duplicates; effect cleanup prevents old reads or sign-out acknowledgements from updating a newer session.

Workspace bootstrap publishes a complete snapshot only after the fresh cookie-authorized membership list and the selected agency's leads succeed. Selection resolves the requested tenant from that fresh list, including its current role/name/timezone. Removed access cannot silently open another agency. An explicit agency-list refresh shows choices without eagerly reading their leads. The component key includes user/tenant/role. Malformed membership/lead snapshots fail before publishing any workspace data.

HTTP 401 requires sign-in; 403, 429 and unavailable/malformed/network responses show a recovery screen with retry and fresh agency choices. A successful sign-in followed by a failed bootstrap goes to recovery rather than reporting sign-in failure. Failed sign-in/signup/reset requests retain the login form inputs. Recovery hides protected workspace records and does not simulate preview data.

Agency creation retains an account/path/method/payload retry identity through both the save and required bootstrap. Failed refreshes keep the onboarding form and its entered values. An observed account change rejects the old-account follow-up before reading leads and clears its receipt through auth reset. Identity remains in mounted memory only; after reload inspect existing agencies before repeating an uncertain creation. Server cookie identity, SQL replay scope and current membership remain authoritative, including changes between successive requests.

Sign-out clears mounted agency/leads/membership and creation retry state before the POST. Only signed_out=true acknowledges completion. Errors or unknown acknowledgements stay on a retry sign-out screen without reopening cached records or accepting a login action in that mounted session. This does not prove server cookie invalidation on failure, prevent a separate tab/reload from using an existing cookie, or cancel a committed server mutation.

They cover zero/single/multiple memberships, fresh roles, revoked selection, explicit agency choice, auth versus outage classification, delayed membership/lead/sign-out responses, malformed snapshots, account changes, creation refresh failure and account-scoped retry identity. ## Invitation and authenticator recovery

The eleventh P8 slice applies abort/generation tickets and the synchronous action gate to /join and Account security. An InvitationFragment object reads the private fragment once per mounted page, scrubs valid or invalid fragments from address history and keeps only the validated token in memory. Effect replay therefore cannot lose a valid token when the URL has already been scrubbed. Duplicate token parameters are rejected; an accepted invitation clears the memory holder permanently. Reload/navigation still requires reopening the original private link. No token or setup key is written to browser storage.

Join checks the current verified account before acceptance and binds in-memory retry identity to user/path/method/token/display name. Lost or malformed acceptance acknowledgements retain that identity and the entered form; only a concrete tenant/membership receipt acknowledges acceptance. Server SQL still checks current verified identity, matching invitation email, consumed actor, active membership, MFA, expiry and replay payload. A client identity read is not an atomic cross-tab cookie lock. Observed account changes clear the old retry and account/MFA view. Delayed reads/accept/sign-out results cannot revive an unmounted generation. A backend outage shows an account-check retry instead of silently assuming sign-out. Switching account hides the old account/MFA component immediately and requires explicit sign-out confirmation; uncertainty retains a retry screen and token in mounted memory.

Account security validates factor inventory and recent status before enabling actions, exposes manual refresh and fences every read/write. Select/enroll/clear/verify actions share the synchronous gate; selectors are disabled while busy. Enrollment first reads fresh factors and refuses another POST when any verified or unfinished authenticator exists. Only the minimized factor ID, bounded private secret and base64 SVG image are retained from enrollment. Auth denial clears private factors/setup state; ignored-abort late responses cannot publish QR/key data.

Enrollment is a non-idempotent Auth operation. Unknown transport or malformed setup results trigger a factor-list read, never an automatic second enrollment POST. The mounted client keeps an uncertainty hold; users can explicitly clear their own unfinished factor or verify an existing factor before enrolling again. If no factor appears, reopening Account security resets mounted state and the next explicit enrollment still preflights. This is not exactly-once enrollment across tabs, navigation or delayed Auth commits. Missing QR/key cannot be reconstructed from a factor inventory. Verified factor removal and recovery/admin resets remain out of scope.

After verify/clear, the private setup key is hidden and further actions wait for a fresh factor snapshot. Failed verification preserves the entered six-digit code; the form resets only after the full successful current workflow. A successful Auth write followed by failed refresh requires manual factor refresh rather than an unverified recent-status claim.

## Lead-detail parent workflow recovery

The fourteenth P8 slice retains the redesigned lead workspace and adds a lead/agency/role-scoped request controller. Initial and recovery loads publish a complete six-request snapshot only after current-scope, lead/tenant identity, row/page structure, role and lead/control-version checks pass. Role changes require reopening the workspace. Initial load failure hides editable content; later temporary failures retain mounted parent forms in an inert state. Current 401/403/404 clears messages/tasks/activity/directory, cursors, summary, editors, pending save and visible modal identity. Current server authorization remains authoritative; this does not erase the parent inbox, cancel an already committed mutation or prove cookie invalidation.

Parent contact/status/assignment/archive/contact-preference, conversation log/revision and follow-up create/action workflows share a synchronous action gate. History and paging also use abort/generation tickets. Stale results cannot publish state, reset forms, close editors or display a saved notice. Section navigation is disabled while the parent action or unresolved save is active so its form stays mounted. On temporary failure, the explicit recovery action replaces repeating a form submission.

A pending replayable save keeps its original request body and key in mounted memory. Unknown write acknowledgements retry that original operation even if an independent read has changed the displayed version. A verified write followed by failed snapshot load enters a read-only recovery phase; successful recovery performs no additional mutation and only then runs the original form-reset/editor-close callback. Malformed write success cannot acknowledge completion. Definitive input/conflict/access responses release the pending write; authorization failures also reset private detail state. No attempt or customer text is stored in browser storage. Closing/reloading the page discards mounted retry state; inspect saved records before repeating uncertain work after navigation.

The existing contact/budget PATCH is version guarded but does not implement an idempotency receipt. After an uncertain response its recovery only loads the latest saved details and asks the user to review them before submitting again; it neither repeats PATCH nor claims the earlier save succeeded. Other parent replay operations retain their existing SQL authority/replay checks. Facts, analysis and reply-draft child workflows keep their existing request/recovery behaviour; this slice does not establish cross-panel/cross-tab serialization.
