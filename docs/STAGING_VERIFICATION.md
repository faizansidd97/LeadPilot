# Read-only staging baseline

P8 provides an operator checker for the configured staging project's public Auth settings and anonymous table permissions. Initially tested with injected transport and isolated PostgreSQL fixtures; on 2026-10-10 the user permitted read-only API checks and the corrected checker passed the configured development baseline recorded in DEV_BASELINE.json. A passing baseline is not migration, authenticated workflow, scheduler, provider, browser or release acceptance.

From `backend`, run `pnpm verify:supabase --help` to review the options. Connecting requires `pnpm verify:supabase --connect-staging --staging-config <private-staging-env-file>`. The file must provide `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`; it replaces ambient environment values. Without a file argument, explicitly connected checks use the process environment. The checker no longer implicitly loads `frontend/.env.local`. Without the connection flag it exits BLOCKED before reading configuration or making requests. Follow existing environment access permissions before running connected commands.

Only an HTTPS base URL without embedded credentials, path, query or fragment is accepted; loopback staging hosts are rejected. Public publishable keys or legacy anon-role JWT keys are accepted. Private service-role and authenticated-user keys are rejected before transport. Only the public key is sent; a separate service key in configuration is ignored.

The Auth settings check requires explicit boolean values for enabled email signup, signup enabled and email autoconfirm disabled. Missing, malformed or unsafe settings fail. This does not prove the actual confirmation email, callback, TOTP or session workflow.

The table inventory covers agencies, memberships, leads, messages, activity_events, follow_ups, invitations, notifications, message_revisions, ai_jobs, ai_analyses, reply_drafts, draft_feedback, privacy_cases and privacy_case_actions. Local tests compare this inventory with every migrated public table and execute real anonymous `SELECT id ... LIMIT 0` queries expecting PostgreSQL permission denial. New public tables require inventory updates.

Each remote table probe uses GET with the public schema, `select=id&limit=0`, no Authorization session, no caching, redirect rejection and an eight-second timeout. Only HTTP 401 or 403 with exact code 42501 satisfies the table denial check. PostgREST uses 401 for anonymous privilege denial and 403 for authenticated denial. Empty HTTP 200, missing tables, other 401/authentication errors, unexpected statuses and malformed responses fail. Successful table bodies are cancelled without reading them. Parsed settings/error bodies are bounded to 16 KiB. Reports contain fixed check names/reasons, never remote messages, response bodies, project URLs or keys. Subsequent probes continue after individual failures so the operator sees the complete baseline.

Exit 0 reports BASELINE_PASS; exit 1 reports BASELINE_FAIL or configuration/options BLOCKED. Every report explicitly leaves authenticated_acceptance, migration_revision_verified, worker_verified, browser_accepted and release_accepted false. Existence of all tables cannot establish migrations 015–018, RPC definitions, indexes, grants on functions or current schema revision. Complete those separately through the staging acceptance procedure in RELEASE_CHECKLIST.md.

Focused local tests cover request minimization, strict Auth configuration, invalid URL/key rejection before transport, open/missing tables, body cancellation, malformed/oversized responses, transport failures, safe CLI behavior, migrated inventory parity and actual anonymous SQL privileges. Hosted Auth/RLS/MFA/two-agency API/UI/direct RPC, scheduler/email/provider, real concurrency/restore and human review remain pending. This tool never creates accounts, applies SQL, submits jobs, invokes mutation RPCs, sends email or changes policies.

The 2026-10-10 read-only baseline passed all 16 checks without account creation, email, SQL mutations, worker/provider execution or browser automation. Anonymous denial does not prove relation existence/current migrations or signed tenant policies. See DEV_BASELINE.json and AUTH_RECOVERY.md; all acceptance fields remain false.
