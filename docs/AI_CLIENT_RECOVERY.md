## Saves and retained input

Each mounted agency/lead/role panel owns a request controller and a synchronous action gate shared with the lead dialog. Analysis and draft reads, pagination and writes cannot overlap. Replaced/unmounted requests cannot publish data, acknowledge saves, reset inputs or continue clipboard receipts, even if a transport ignores abort. The parent cannot reload or change sections while a child action or recovery is active. Closing is blocked while work is running; closing an idle recovery discards its in-memory state, as the panel explains.

An uncertain acknowledgement retains the original serialized body, expected versions, method, endpoint and idempotency key. Only the explicit Recover action retries that original operation. Refresh cannot retry an uncertain write or clipboard operation. Other writes and input changes remain disabled until recovery completes or a definitive input/version denial releases it. After a validated acknowledgement, any failed history refresh retains a read-only recovery; it never repeats the write. Generation options, local working text, feedback/rejection comments and actual external-message inputs stay mounted across recoverable failures. Completion and parent callbacks wait for current confirmed history and run after the shared gate is released. Version conflicts require a fresh read and explicit comparison/rebase of retained text.

History schemas project the display fields, bound pages to 25 jobs/results, bind the lead and result agency/job/context, validate IDs/states/versions/timestamps, score consistency, freshness, job ordering and cursor identity. Older pages cannot mix changed context, availability or permissions. Acknowledged historical jobs/drafts are reconciled through at most 20 pages; missing or older-than-receipt state leaves explicit read recovery available. A fresh first-page refresh resets history paging, preserves local editor input and exposes retained text if its saved draft is outside that page. Definitive 401/403/404 denial clears private histories/forms/recovery and informs the parent.

Jobs' history projection and cancellation/submission receipts do not contain tenant/lead fields. Their authority remains the verified server request/RLS scope; the client additionally confirms the returned job ID in that scoped history and, for cancellation, its terminal state/minimum version. Client validation supplements server authorization.

## Clipboard boundary

Copy retains a snapshot of the reviewed draft and a distinct original authorization key and copied-receipt key. Authorization must match the saved text/version and contain a valid unexpired UUID token before local clipboard access. Clipboard permission failure never issues COPY_DONE; explicit recovery reauthorizes with the same original key before trying local copy again. After local copying succeeds, the original receipt body/key is retained: receipt uncertainty retries COPY_DONE without reauthorizing or copying again. A confirmed receipt followed by failed history refresh performs only reads. The UI distinguishes local copying from receipt confirmation and never treats copying as an external sent message.

Unmount during an already-running OS clipboard operation cannot undo that OS action; current-request fencing prevents subsequent receipt requests or UI completion. This is not an OS clipboard rollback guarantee. A definitive conflict/expired receipt requires a fresh read and deliberate review. Pending state, tokens and input live only in mounted memory, with no browser storage or durable client retry queue.

Polling performs reads every 30 seconds only while the document is visible, the panel is idle/ready, no recovery is pending and queued/running jobs exist. A failed read stops polling and requires explicit refresh. Polling never retries writes. Logging actual sent text remains an explicit confirmed user report; the shared frontend/server schema checks the past timestamp, and the nested SQL receipt binds exact text, scope and next lead version.
