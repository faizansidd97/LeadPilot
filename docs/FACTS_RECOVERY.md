# Confirmed facts and duplicate-review recovery

The Facts section now retains entered facts and duplicate-review reasons through recoverable save/read failures. A save captures its parsed fields, expected version and serialized body before awaiting the network. **Recover original save** uses the same operation, body and request key after an uncertain acknowledgement. A verified acknowledgement advances recovery to **Load saved facts**, which repeats reads only. Saved feedback and the submitted form reset happen only after a fresh, current lead read succeeds.

Facts form identity changes after its successful save or an explicit **Reset to saved facts** action. Parent reloads and duplicate resolution can update the authoritative lead/version without discarding separately entered facts. Duplicate-review input is not cleared by an ordinary facts save. Version conflicts release the failed write and require **Load latest facts**; retained values must be reviewed before another explicit save. This adds no automatic writes or merges.

The workflow is mounted by agency, lead and role. Abort/current-generation tickets fence ignored-abort responses, scope changes and unmounts. Synchronous child action locking and parent/child callbacks block overlapping reloads, saves and section changes while a facts action or original-save recovery is pending. Close/Escape is blocked during active requests; closing an idle panel, switching scope or reloading the application discards mounted input and recovery memory. No customer input is persisted in local storage.

Lead receipts bind agency, lead and the exact next version; duplicate-resolution receipts must confirm review is cleared. Refreshed leads cannot predate the acknowledged write. Validated workspace fields are projected before publication. Candidate reads bind the request's agency/lead and manager role, validate bounded ordered UUID pages/cursors and project only the candidate fields consumed by the UI. The existing candidate API does not return tenant/parent metadata on individual matches; SQL authorization and request scope remain authoritative. Agent and restricted responses cannot publish matching identities.

Failed candidate reads show an unavailable state, preserve previously loaded matches with visible failure feedback and disable resolution until a successful review. Empty-match feedback requires a successful empty response. Definitive access/not-found errors clear matching identities and notify the parent to hide protected lead detail. Archived leads remain read-only; server membership, versions, replay and audit protections are unchanged.
